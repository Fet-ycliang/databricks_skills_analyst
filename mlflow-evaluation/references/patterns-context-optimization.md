## 為何上下文優化很重要

上下文視窗是有限且昂貴的。糟糕的上下文管理會導致：
- **Token 膨脹**：為冗餘或低價值的 Token 付費
- **遺失上下文**：重要資訊被冗長的內容擠出
- **品質下降**：模型的注意力被不相關的內容稀釋
- **延遲**：較大的上下文 = 較慢的推論

## 策略 1：工具結果管理

工具呼叫通常會返回冗長的 JSON，迅速填滿上下文視窗。

### 問題
單個工具呼叫可能返回 5,000+ Token 的 JSON 資料，但代理回應實際只需要 50 個 Token。

### 解決方案

**選擇性欄位提取**
- 在將工具結果返回給代理之前，僅提取所需的欄位
- 為每種工具類型定義「必要欄位」（例如，對於搜尋工具：標題、摘要、url）
- 丟棄詮釋資料 (metadata)、除錯資訊和冗餘欄位

**結果截斷**
- 將陣列結果限制為前 N 個項目（例如，前 10 個搜尋結果，而不是 100 個）
- 將長文字欄位截斷為前 N 個字元
- 將大型資料集總結為聚合資料（計數、平均值、範圍）

**結構化摘要**
- 將原始工具輸出轉換為自然語言摘要
- 「找到 47 個結果。前 3 名：[公司 A] (45% 成長), [公司 B] (32% 成長), [公司 C] (28% 成長)」
- 保留關鍵事實，丟棄 JSON 的冗長性

### 何時應用
- 在工具執行後立即應用，在加入上下文之前
- 對較舊的工具結果更積極地應用，對最近的結果保留細節

## 策略 2：訊息歷史壓縮

對話歷史隨著每一輪增加。管理它對於多輪代理至關重要。

### 第 1 層：滑動視窗 (Sliding Window)
僅保留最後 N 條訊息，丟棄舊的。

| 優點 | 缺點 |
|------|------|
| 實作簡單 | 遺失歷史上下文 |
| 可預測的上下文大小 | 可能破壞對話連續性 |
| 無額外延遲 | 使用者引用舊內容會失敗 |

**最適合**：簡單聊天代理、短對話、無狀態互動

### 第 2 層：過濾 + 總結
過濾冗長訊息，建立舊內容的摘要。

| 優點 | 缺點 |
|------|------|
| 保留關鍵資訊 | 需要提取邏輯 |
| 良好的壓縮率 (50-70%) | 一些細節遺失 |
| 維持連續性 | 增加複雜度 |

**最適合**：工具呼叫代理、多步驟任務、中等長度對話

### 第 3 層：語義壓縮 (Semantic Compression)
使用 LLM 總結較舊的對話片段。

| 優點 | 缺點 |
|------|------|
| 最高壓縮率 (70-85%) | 增加延遲 (LLM 呼叫) |
| 很好地保留意義 | 摘要需要 Token 成本 |
| 處理複雜上下文 | 可能遺失細微細節 |

**最適合**：非常長的對話、定期檢查點、複雜的多代理工作流程

### 混合方法
根據訊息年齡結合各層：
- **最近 (最後 5-10 條訊息)**：保留逐字
- **中等 (10-30 條訊息前)**：第 2 層過濾
- **舊 (30+ 條訊息)**：第 3 層語義摘要

## 策略 3：結構化狀態 vs 訊息歷史

與其傳遞完整的訊息歷史，不如維護捕獲對話語義的結構化狀態。

### 訊息歷史方法
```
[Message 1: User asks about X]
[Message 2: Assistant responds]
[Message 3: Tool call result - 2000 tokens of JSON]
[Message 4: Assistant analyzes]
[Message 5: User follow-up about Y]
...
```
線性增長，包含冗餘。

### 結構化狀態方法
```
{
  "topic": "X analysis",
  "entities_discussed": ["Company A", "Company B"],
  "filters_applied": {"time_range": "Q3 2024"},
  "key_findings": ["Finding 1", "Finding 2"],
  "last_query": "Y follow-up"
}
```
固定大小，捕獲語義。

### 權衡

| 面向 | 訊息歷史 | 結構化狀態 |
|--------|-----------------|------------------|
| 大小增長 | 線性 | 有界限 |
| 上下文豐富度 | 高 | 中 |
| 實作 | 簡單 | 複雜 |
| 錯誤恢復 | 容易 (重播) | 較難 |
| 多輪連貫性 | 自然 | 需要設計 |

### 建議
使用結構化狀態於：
- 長時間執行的對話 (10+ 輪)
- 多代理系統 (在代理間傳遞狀態)
- 串流上下文 (狀態可序列化/恢復)

使用訊息歷史於：
- 短互動 (< 10 輪)
- 簡單問答代理
- 當真正需要完整對話上下文時

## 策略 4：上下文效率的提示工程

系統提示本身可能使上下文膨脹。優化它。

### 避免冗餘
- 不要重複範例中隱含的指令
- 不要包含涵蓋相同情況的範例
- 引用外部文件而不是內聯它們

### 使用階層式指令
```
## Core Rules (always apply)
- Rule 1
- Rule 2

## Situational Rules (apply when relevant)
- If X, then Y
- If A, then B
```
代理可以在心理上跳過不相關的部分。

### 動態提示組裝
根據上下文組裝，而不是使用單一龐大的系統提示：
- 基礎指令（始終包含）
- 工具特定指導（僅當工具被綁定時）
- 領域上下文（僅當與查詢相關時）

### 測量提示 Token 成本
追蹤以下使用的 Token：
- 系統提示（每個請求的固定成本）
- Few-shot 範例（固定成本）
- 對話歷史（可變）
- 工具結果（可變，通常最大）

## 策略 5：智慧快取

透過快取避免冗餘運算和 Token 使用。

### 結果快取
- 快取相同查詢的工具結果
- 根據資料新鮮度需求設定 TTL
- 在相關狀態變更時失效

### 摘要快取
- 快取計算出的對話片段摘要
- 當該片段未變更時重用
- 對於第 3 層語義摘要特別有價值

### 提示快取 (模型層級)
一些提供者快取提示前綴：
- Anthropic：對重複提示自動前綴快取
- OpenAI：對相同前綴序列的提示快取

結構化提示以最大化快取命中：
- 將穩定的內容（系統提示、範例）放在最前面
- 將可變內容（對話、工具結果）放在最後

## 策略 6：壓縮觸發器

不要每一輪都壓縮——需要時才壓縮。

### 基於訊號的觸發器
- **Token 計數**：當估計 Token > 閾值時壓縮
- **訊息計數**：當訊息 > 閾值時壓縮
- **輪次計數**：每 N 輪壓縮一次
- **基於時間**：對話 N 分鐘後壓縮

### 閾值指南

| 代理類型 | Token 觸發器 | 訊息觸發器 |
|------------|---------------|-----------------|
| 簡單聊天 | 80K | 30 條訊息 |
| RAG 代理 | 40K | 15 條訊息 |
| 工具呼叫 | 50K | 20 條訊息 |
| 多代理 | 30K | 10 條訊息 |

### 避免過度壓縮
- 在有意義的內容可壓縮之前不要壓縮
- 保持最近上下文完整（最後 5-10 條訊息）
- 驗證壓縮不會破壞代理行為（使用評估進行測試）

## 策略 7：架構特定模式

### 對於多代理管線
- 每個代理應僅接收其所需的上下文
- 在階段之間傳遞結構化摘要，而非完整歷史
- 最終的「執行者」階段可能比「分類器」需要更多上下文

### 對於 RAG 代理
- 檢索到的文件通常占據大部分上下文
- 限制返回的區塊（前 3-5 個，而不是 10+）
- 在加入上下文之前總結檢索到的內容
- 在檢索前考慮相關性過濾

### 對於串流代理
- 上下文必須可序列化以進行恢復
- 偏好結構化狀態而非訊息歷史
- 在序列化檢查點之前壓縮

## 上下文優化的指標

追蹤這些以測量優化有效性：

| 指標 | 測量什麼 | 目標 |
|--------|------------------|--------|
| 每個請求的 Token | 上下文效率 | 最小化 |
| 壓縮率 | 壓縮前後 Token 比 | 0.3-0.7 |
| 壓縮後評估分數 | 品質維持 | 無回歸 |
| 延遲影響 | 壓縮開銷 | < 100ms |
| 快取命中率 | 避免的冗餘運算 | > 50% |

## 常見陷阱

### 1. 過於積極地壓縮
**症狀**：代理無法回答後續問題
**修正**：保留最近訊息，使用多輪評估進行測試

### 2. 忽略工具結果大小
**症狀**：單個工具呼叫填滿上下文視窗
**修正**：立即截斷/總結工具結果

### 3. 代理間的冗餘上下文
**症狀**：多代理系統將相同內容傳遞給每個階段
**修正**：為每個代理角色量身定製上下文

### 4. 無壓縮測試
**症狀**：壓縮破壞邊緣情況
**修正**：在評估資料集中包含壓縮場景

### 5. 靜態閾值
**症狀**：對某些查詢有效，對其他查詢失敗
**修正**：使用多訊號觸發器（Token AND 訊息 AND 時間）

---

## 實作優先順序

實作上下文優化時：

1. **從工具結果開始** - 通常是以最低努力獲得最大收益
2. **加入滑動視窗** - 簡單的訊息限制防止失控增長
3. **實作結構化提取** - 在過濾前捕獲關鍵事實
4. **加入壓縮觸發器** - 僅在需要時壓縮
5. **考慮語義總結** - 用於複雜、長時間執行的對話
